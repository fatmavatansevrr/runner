## 1. Question 1 — Pattern continuity ordinal across GE → Runway → Core

### Resolution: **APPROVED — `GlobalStructuralWeekOrdinal` confirmed as already-frozen authority, not new invention**

This is not a new decision this phase invents. `GEN.11 §1` already froze it, in these exact words:

> "Pattern continuity across GE→Runway→Core (LongHorizon): the handoff's recommendation (§11) to key the pattern off a **global structural week ordinal** spanning all three segments — not resetting per segment — is adopted. This is directly analogous to the existing `GlobalWeekNumber` concept `LongHorizonStructuralWeek`/`LongHorizonStructuralMaterializer` already use for every other frequency's structural skeleton."

This phase's job was to verify that citation against real code and against `FREQ.6D.11`-`22`'s real precedent, not to accept it at face value — done:

**Real-code verification.** `LongHorizonStructuralMaterializer.cs` constructs three `LongHorizonStructuralWeek` records — one per segment builder (GE at line ~216, Preparation Runway at line ~309, Core at line ~359) — and every one of the three carries both a `GlobalWeekNumber` (threaded through from a single running counter across all three segment-builder calls) and a `LocalSegmentWeekNumber` (the segment-relative week index, e.g. `ge.WeekIndex`, `rw.RunwayWeekNumber`, `cw.WeekNumber`). This is a real, already-existing, already-used-for-every-other-frequency mechanism — not a hypothetical GEN.11 invented from nothing. **`GEN.11`'s citation is accurate.**

**`FREQ.6D.11`-`22` precedent check (the actual required work of this question).** `FREQ.6D.11` is the real, deepest cross-segment continuity architecture this codebase has ever built (Intermediate×5D LongHorizon dual-KEY lineage). It solves a *different* granularity of the same class of problem — per-session identity within a week (`(StructuralRole, LaneOrdinal, SlotOrdinal)`, §13/§28 of that report) rather than which-week-is-A/B — but its governing principle transfers directly and is the correct lens to re-verify `GEN.11`'s ordinal choice against:

- `FREQ.6D.11 §14`/`§21`/`§22` establish, as hard-won architecture law (discovered via a real, demonstrated collision, `§8`'s `CURRENT_5D_JIT_COLLISION_TRACE`): identity that determines "which slot is which" **must be a persisted invariant, assigned once, and never independently recomputed** by JIT materialization, restart, or repair — because if two subsystems each recompute it locally (there: `BuildBoundedCoreSelection`'s FIFO-by-date dequeue effectively re-deriving lane identity from date order), they can disagree, and nothing downstream can detect the disagreement (§8: "the wrong lane's workout/profile could be dequeued into the wrong physical slot ... neither the resulting row nor any downstream consumer could detect or correct it").
- Applied to Question 1's actual object (week parity, not session lane): the identical failure mode is real and concrete, not hypothetical. LongHorizon's GE segment is variable-length (`AvailableFullWeeks - 20`, `LongHorizonCompositionResolver.LongHorizon`, confirmed unchanged by `FREQ.6D.11 §25`). If Runway or Core each independently computed "my own local week 1 is Pattern A" (a locally-reset parity) rather than continuing the parity inherited from wherever GE's variable length left off, the athlete would see a visible pattern discontinuity at the segment boundary (e.g., two Pattern-A weeks or two Pattern-B weeks in a row) — and JIT materialization (computing the boundary week live), a restart (reconstructing state from persisted rows), and a repair (regenerating a future week after an adaptation event) could each independently reach a different answer for the exact same boundary week, with no mechanism to detect the disagreement, exactly mirroring `FREQ.6D.11 §8`'s dual-KEY collision in shape.
- `GEN.11`'s `GlobalStructuralWeekOrdinal`/`GlobalWeekNumber` is precisely the `FREQ.6D.11`-style fix for this failure mode: a single, persisted, monotonically-continuing ordinal assigned once (at structural-skeleton materialization time, per `LongHorizonStructuralMaterializer`'s existing behavior for every other frequency) that both Runway and Core read rather than each re-deriving "week 1" locally. It is the same architectural instinct as `FREQ.6D.11`'s `LaneOrdinal`/`SlotOrdinal` (persist an invariant once, consume it everywhere, never recompute), applied one level up the identity hierarchy (week-level parity instead of session-level lane).

**Conclusion**: **No `DOMAIN_DECISION_REQUIRED`.** `GEN.11`'s `GlobalStructuralWeekOrdinal` (= the existing `GlobalWeekNumber` field on `LongHorizonStructuralWeek`) is confirmed, both by direct code trace and by `FREQ.6D.11`'s real precedent, as the correct mechanism — not merely "sounds clean," but structurally the same fix the one real precedent in this codebase already proved necessary for an analogous cross-segment identity-continuity problem. Pattern reset = NEVER across any phase transition; taper is the sole structural override (unchanged from `GEN.11 §1`/`§5`). This phase formalizes (does not re-litigate) `GEN.11`'s authority, and additionally establishes the specific citation-worthy precedent (`FREQ.6D.11 §8/§14/§21/§22`) that was not cited when `GEN.11` first adopted it.

**Distinction preserved, not conflated**: `FREQ.6D.11`'s `(StructuralRole, LaneOrdinal, SlotOrdinal)` model answers "which session, within one week, does this data belong to" (dual-KEY disambiguation) — an orthogonal axis to `GlobalStructuralWeekOrdinal`'s "which week, across the whole plan, is this." 2D has no dual-KEY question (Model B is single-lane by construction, `GEN.11 §1`), so `FREQ.6D.11`'s session-identity fields do not themselves need to be reused for 2D — only its underlying *design principle* (persist, don't recompute) does, and that principle is what already-frozen `GlobalWeekNumber` satisfies.

## 2. Question 2 — Runway structural continuation vs prescription model

### Resolution: **Hypothesis (a) APPROVED — structure identical to Core, KEY prescription content/intensity differs; Runway's quality-density-reduction principle is explicitly NOT applied by removing 2D's structural role**

`GEN.11 §4` already froze the structural half of this question in one sentence that this phase re-verifies rather than assumes correct:

> "Preparation Runway (15-20wk): SUPPORTED for both levels ... **Runway retains the same A/B pattern** (handoff §14.2) rather than a separate frequency ramp — consistent with every other frequency's Runway design (Runway is a fixed-length lead-in to the same Core numeric authority, not a separately-calibrated numeric system)."

**Required work — testing this against the "quality-density-reduction" principle used for 3D+, not assuming it transfers.** The prompt is correct to be suspicious: that principle has a real, traceable origin, and it was never calibrated for an input this low.

- **Where the principle actually comes from**: `FREQ.6D.6` approved Intermediate×5D Preparation Runway's weekly structure as **1 KEY + 3 EASY + 1 LONG** — a *single*-KEY shape, explicitly a reduction from Core's own **2 KEY + 2 EASY + 1 LONG** dual-KEY shape (`FREQ.6D.8`/`FREQ.6D.10` wire the same reduced structure into real Runway execution; `FREQ.6D.23`/`FREQ.6D.25`/`FREQ.6D.26` extend the identical "Runway = Core minus the second KEY lane" shape to 6D). The mechanism the principle actually implements is: **remove exactly one of Core's multiple KEY lanes during the fixed 8-week Runway lead-in**, keeping every other structural role (EASY count, LONG) at Core's own cardinality. It has only ever been exercised on frequencies with **two or more** KEY lanes in Core (5D, 6D) — it removes a lane that has a sibling.
- **Why it cannot mechanically transfer to 2D**: 2D's Core already has **at most one** `KEY_SESSION` per week, and only on every *other* week (Pattern A); Pattern B weeks already have **zero** `KEY_SESSION` slots. There is no second KEY lane to remove. A literal, unexamined reuse of "reduce quality density for Runway" would have to mean *removing 2D's only KEY_SESSION slot entirely* — i.e., a Runway with **zero** quality sessions across its entire 8 weeks, alternating `EASY_SUPPORT + LONG_RUN`/`EASY_SUPPORT + LONG_RUN` (an A-week collapsing into a second B-week shape). This is a materially different, far more aggressive reduction than what the principle does for 5D/6D (which always keeps ≥1 KEY lane), and this phase finds **no evidence anywhere in `FREQ.6D.6`/`.7`/`.8`/`.10`/`.23`/`.25`/`.26` that the principle was ever designed, evaluated, or intended to answer "what happens when reducing further would eliminate quality work altogether."** The prompt's caution is justified and is explicitly recorded here, not silently bypassed.
- **What `GEN.11` already decided instead, and why it is the right call**: `GEN.11 §4` does not attempt to extend the lane-removal mechanism to 2D at all — it holds Runway's *structure* fixed at Core's own A/B shape and treats Runway purely as "a fixed-length lead-in to the same Core numeric authority, not a separately-calibrated numeric system." This is Hypothesis (a): **structure identical to Core; only the numeric/prescription content within the existing KEY slot is Runway-owned/controlled** (i.e., whatever intensity-control convention Runway prescriptions use elsewhere — a reduced or introductory-intensity variant of the KEY workout content, never a change to which structural role occupies which week). Hypothesis (b) (removing/restructuring the KEY slot itself for Runway specifically) is **rejected**: it would require inventing a genuinely new structural pattern with no precedent (2D's Pattern-B-only Runway), directly contradicting `GEN.11`'s own frozen, user-approved Model B definition being "frequency-owned, shared identically by Beginner and Intermediate" across Core *and* Runway (§1), and would leave a 2D athlete with literally zero KEY-intensity exposure during the entire Preparation Runway phase — a materially different athlete experience than any other frequency's Runway ever produces (every other frequency's Runway retains ≥1 KEY/week specifically to avoid this).
- **Evidence-basis honesty requirement satisfied**: this phase explicitly records, per the prompt's own instruction, that the reduce-quality-density principle "was not designed with a frequency this low as an input" — this is not silently assumed away. It is not treated as a blocker because `GEN.11` already resolved the actual applicable question (structure continuity) independently of that principle, by a different, already-approved argument (Runway-as-fixed-lead-in-to-Core, not Runway-as-separately-ramped-numeric-system) that does not depend on lane-removal at all.

**Conclusion**: **No `DOMAIN_DECISION_REQUIRED`.** Hypothesis (a) is confirmed correct on the evidence: 2D Runway's A/B structure is byte-identical to Core's (same `GEN.11`-frozen Model B, continuing the same `GlobalStructuralWeekOrdinal` from Question 1), and only the KEY-slot's prescription intensity is Runway-owned/controlled — exactly the same "Runway = numerically distinct, structurally identical to Core" relationship every other frequency's Runway already has, and exactly what `GEN.19`'s later architecture-gap finding is scoped around (a materialization-mechanism gap, not a structural-content gap — see Question 3 discussion below). The 5D/6D-style lane-removal "quality-density reduction" mechanism is explicitly **not** applied to 2D and should not be invoked again for 2D in any future implementation phase.

**Conclusion**: **No `DOMAIN_DECISION_REQUIRED`.** The three target-capped/readiness-aware/GE→Runway→Core principles are confirmed to apply to 2D exactly as `GEN.11`/`FREQ.6D.12`/`FREQ.6D.14` already established.
