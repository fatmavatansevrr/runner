## 2. The real, newly-confirmed architecture gap: Preparation Runway has no repeating-pattern mechanism

`GEN.11 §14.2` explicitly required 2D's Preparation Runway to retain the same Model B A/B alternation as Core ("Runway retains the same A/B pattern... consistent with every other frequency's Runway design"). This phase investigated whether the real Runway materialization architecture can express that requirement, and found it genuinely **cannot**, in its current form:

- `TenKPreparationRunwayWeekMaterializationPolicyFactory.BuildLayout(int daysPerWeek)` (`backend/RunningApp.Application/RuntimeCatalog/Schedule/PreparationRunwayWeekMaterialization/TenKPreparationRunwayWeekMaterializationPolicyFactory.cs:30`) returns exactly one `PreparationRunwayCanonicalWeeklyLayout` — a single, static, ordered list of `PreparationRunwaySlotRole` values (e.g. 4D: `[KeySession, EasySupport, EasySupport, LongRun]`) — applied identically to every week of the entire 8-week Runway, for every existing frequency (3D/4D/5D/6D). There is no week-parity, no pattern-period, no per-week-varying role concept anywhere in this factory or its consumers.
- `BuildBlockRolePolicies()` (same file, lines 79-103) is a second, independent mechanism governing which **block-relative week position** (1st, 2nd, ... week within a Consistency/GeneralEndurance/AerobicStrength/PreSpecificTransition block) receives which **role at a specific slot ordinal** (e.g. Consistency block week 1 → `KeySession`, week 2 → `LongRun`) — this operates on top of the single static `BuildLayout` role list, not in place of it, and has no notion of alternating a week's *entire* non-long role by parity either.
- `PreparationRunwayCalendarComposer`/`PreparationRunwayCalendarSkeletonAdapter` (`backend/RunningApp.Application/RuntimeCatalog/Schedule/PreparationRunwayCalendarComposition/`) both consume `DaysPerWeek` only as a slot-count parameter for calendar day-assignment — no pattern-awareness exists there either, confirming the gap is architectural (missing from the data model these consumers read), not merely absent from one call site.

**This is the exact same class of gap `GEN.11 §1` originally found and disclosed for Core's `RunLayout`/`ICatalogRunLayoutResolver`** ("every existing `RunLayout` document declares exactly one fixed weekly `slots[]` array... 2D genuinely cannot be represented by a single static `slots[]` array") — `GEN.12` closed that gap for Core with `WeeklyPatternRoles`/`PatternPeriodWeeks` (two new optional fields, `null` for every pre-`GEN.12` candidate, threaded through `CatalogStageToWeekMaterializer.ResolveWeekRoles`). **Preparation Runway is architecturally independent of that fix** — it has its own separate data model (`PreparationRunwayCanonicalWeeklyLayout`, `PreparationRunwayBlockWeekRolePolicy`) and its own separate materializer (`PreparationRunwayWeekMaterializer`), neither of which was touched by `GEN.12`'s Core-side work and neither of which has any equivalent repeating-pattern concept today.

**Consequence, stated precisely**: closing this gap for 2D Runway requires *designing*, not merely wiring, an analogous repeating-pattern mechanism for an entirely separate subsystem — a real architectural decision (how does a block's own week-relative role assignment interact with a week-parity-driven role alternation across an 8-week horizon that spans four distinct block types of varying length?) that this phase has no standing to invent unilaterally, matching the exact STOP discipline `GEN.12 §6` used when it found `ProgressionStageAllocator`'s lane/week-eligibility question was a genuine, non-mechanical design decision (which subsequently required `GEN.13`'s own dedicated classification phase before `GEN.14`-`GEN.17` could close it). This is not a training-methodology/product question the way `GEN.13`'s escalation was — no new evidence or coaching judgment is required, since `GEN.11 §14.2` already froze *that* Runway retains the A/B pattern; what remains undecided is purely a **mechanical software-design question** (how to represent and thread the pattern through Runway's own distinct block/role/calendar pipeline), correctly out of scope for a verification phase to invent on the spot.
