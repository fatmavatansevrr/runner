## 7. Eight production profiles — **not authored**

Real, first attempts to author all 8 approved profiles (per FREQ.6D.4B §15's exact matrix) surfaced two structural, previously-latent domain-validation contradictions, proven with real repository evidence (`Intermediate5DProductionPrescriptionCatalogTests.cs`, 15/15 passing):

**Root cause 1** — `GOAL_PACE_TEN_K` (v2 and v3) has never declared `allowedDistanceAccountingModes`. `WorkoutPrescriptionProfileValidator` fails closed (`workout.AllowedDistanceAccountingModes is null` → always rejects, regardless of the profile's chosen `DistanceAccountingMode`). Blocks **RS-P, TAP-P**.

**Root cause 2** — `AEROBIC_STRENGTH_CONTROLLED_INTRO`, `THRESHOLD_TEMPO`, and `FARTLEK` all declare `allowedPrescriptionModes: ["MIXED"]` only — the legacy `PrescriptionMode.Mixed` value never maps to any of the three typed `PrescriptionIntensityMode` values (`PaceBased`/`EffortBased`/`HeartRateBased`) the profile validator checks against. No choice of intensity mode can ever pass `PROFILE_INTENSITY_MODE_NOT_ALLOWED` for these three identities, at **any** version — including the historical v4 versions this phase must not touch, and the new v3/v5 eligibility extensions, which correctly inherit the same `allowedPrescriptionModes` unmodified (changing it would itself violate §6's eligibility-only diff invariant). Blocks **FND-P, FND-S, BLD-P, BLD-S, RS-S, TAP-S** — i.e. every remaining slot.

**Combined: all 8 of 8 approved slots are blocked**, none by a choice this phase is free to make differently.

## 15. Legacy containment — the load-bearing finding of this phase

**A real regression was caught and fixed before commit, not discovered afterward.** Initially authoring all 4 new `WorkoutDefinition` versions with `"status": "VALIDATED"` caused two real, pre-existing golden/consistency tests to fail:

- `WorkoutArtifactImmutabilityTests.CurrentActiveResolution_SelectsPublishedThreeDayClosureVersion_DeterministicallyAndRetirementAware` (for both `THRESHOLD_TEMPO` and `FARTLEK`) — a real golden-fixture assertion that the "current active" version (via the legacy `FindWorkout(key)` highest-non-retired-version resolution, documented in its own doc comment as "exactly the drift-prone behavior documented as a defect... must never be used to assemble a new candidate graph") is **v4**. My new `VALIDATED` v5 immediately outranked v4, silently changing what this resolution returns.
- `DependencyVersionCascadeTests.ActiveCombinationV3_ResolvesAFullyConsistentVersionedGraph` — a real active-combination consistency check expecting `FARTLEK`/`THRESHOLD_TEMPO` to resolve to v4; failed identically for the same reason.

Root cause: `CatalogSourceSnapshot.FindWorkout(key)`'s legacy resolution filters `Status != Draft`, so any `VALIDATED` (or `PUBLISHED`) version — regardless of whether anything actually references it yet — immediately becomes the new "active" resolution result for every legacy consumer of that path. This is precisely the kind of silent behavior change §35 ("Legacy Catalog Containment... Existing WorkoutDefinition historical versions remain immutable") exists to prevent, discovered here as a real, concrete mechanism rather than an abstract risk. **Fix**: set all 4 new versions to `"status": "DRAFT"` — correct both on the merits (none of them is actually usable in production yet, since no profile exists to pair with them) and mechanically (excludes them from the legacy auto-resolution). Re-ran the full suite after the fix: **0 failures**. Intermediate×3D/4D/Beginner×4D remain behaviorally unchanged; historical v2/v4/v4/v2 content is byte-for-byte untouched.
