## 4. Real defects found and fixed during dark verification (implementation-only, documented per this phase's own §64 rule)

1. **`CatalogVolumeAndLongRunPlanner`'s 3D dispatch branch was unconditional on Level** (`daysPerWeek == 3` alone, no Level check) — would have silently routed a future Advanced×3D candidate to Intermediate's own 3D numeric policy. Fixed by restricting the branch to `Level == "INTERMEDIATE"` (its only real caller), with the Advanced branch now handling 3D correctly. Old assumption: any 3D candidate is Intermediate. New: exact `(Level, DaysPerWeek)` match, matching every other frequency's own dispatch style.
2. **`LongHorizonStructuralValidator`'s expected-slot-count dispatch hardcoded exact Intermediate candidate-key strings**, defaulting anything else (including the new Advanced keys) to 4D's shape — silently produced false "wrong slot count" validation failures for every Advanced structural skeleton. Fixed by widening the key-string dispatch.
3. **`PreparationRunwayWeeklyShape.IsValid`'s explicit `ApprovedEasySupportCounts` allow-list excluded 1** — rejected Advanced×3D's genuinely-approved 1K+1E+1L Runway shape outright. Fixed by extending the allow-list, per its own documented convention.
4. **`TenKPreparationRunwayDarkOrchestrator`'s internal candidate-consistency/Level gates were Intermediate-only** (both the candidate-key allow-list and a separate `Level != "INTERMEDIATE"` check) — rejected every Advanced candidate at the very first validation step of both the Runway and the LongHorizon Core-entry paths. Fixed by widening both.
5. **`TenKPreparationRunwayNumericPolicyFactory` maintained its own separate, undiscovered-until-now exact-identity dispatch**, entirely independent of `VolumeSafetyPolicy`'s own dispatch — every non-Intermediate-5D/6D candidate silently fell back to the 4D-shaped numeric policy (0.30-0.36 long-run share) regardless of the candidate's real Level/frequency. This produced a genuine, reproducible failure during the real dark-verification lifecycle test (Advanced×5D's real week-1 long-run share landed at 27.63%, outside the 4D-shaped policy's [30,36]% band it was incorrectly being validated against). Root-caused via direct diagnostic tracing (temporary, reverted throw statements at the exact failure point, per this engagement's established diagnostic-driven debugging technique), not guessed. Fixed by adding the 4 Advanced dispatch arms to this factory's own `Build(candidate)` overload, and by widening its zero-nominal-gap long-run-share-tolerance derivation to include Advanced5D/6D.
6. Consequently, `VolumeSafetyPolicy.Advanced{3D,4D,5D,6D}.GoldenFixtureStartingVolumeKm` was revised from an initial "reuse the PeakVolumeBand minimum directly" calibration (which, once defect #5 was fixed and the real numeric policy correctly applied, still produced a genuine Runway-progression rounding edge case at that exact low starting value — every pre-existing policy's own `GoldenFixtureStartingVolumeKm` sits meaningfully below its band minimum, never at it) to reusing each frequency's own already-proven Intermediate `GoldenFixtureStartingVolumeKm`-to-`ResolvedPeakReference` ratio applied to Advanced's approved peak — a more defensible reuse of an existing deterministic relationship, validated by the same real lifecycle test subsequently passing cleanly.

No new product/numeric/schema authority was introduced by any of these fixes — each is a dispatch/allow-list widening or bug fix within already-approved authority, documented with old assumption / new canonical behavior / regression test per this phase's own §64.
