## 3. GEN.18's 8-9 week boundary: a dedicated, correctly-classified fail-closed check

`GEN.18` proved 8-9 week 2D Core requests deterministically fail deep inside the real allocator (`ProgressionPhaseCapacityInsufficientException`, `RACE_SPECIFIC` shortfall) — a real, correct guard, but one that would surface publicly only as an opaque `PLAN_PREVIEW_GENERATION_FAILED`/500-shaped internal error with no link back to `GEN.18`'s own formal, final non-support classification. Added a new, dedicated, readiness-independent fail-closed check in `V1LiveCatalogPilotRoutingPolicy.Evaluate` (`LivePlanPreviewRouting.cs`), placed before the existing generation pipeline is ever reached: for `DaysPerWeek == 2` and `cycleLength is 8 or 9` at either `Beginner` or `Intermediate`, returns a new route (`CatalogTwoDayCoreEightOrNineWeekFormallyNonSupported`) mapped to a new, distinct typed exception (`CatalogTwoDayCoreEightOrNineWeekNonSupportedException`), whose message explicitly cites `TWO_DAY_CORE_EIGHT_OR_NINE_WEEK_NON_SUPPORT_FORMALIZED_FINAL` and `Phase 10K-GEN.18` by name. Mapped in `GlobalExceptionHandler.cs` to HTTP 422 with error code `TWO_DAY_CORE_EIGHT_OR_NINE_WEEK_NON_SUPPORT_FORMALIZED_FINAL` — the message is echoed verbatim to the client (this repository's own established convention: only 500-status messages are ever suppressed).

This check is deliberately **unconditional on readiness** (unlike the pre-existing Intermediate-4D-specific `KnownInfeasibleEightWeekExplicitZero` short-circuit immediately below it, which only rejects one particular explicit-zero-readiness input at week 8) — `GEN.18`'s finding is that 8-9 weeks fail identically for **every** readiness input at both levels, a real, deterministic capacity shortfall, not a readiness-dependent one. ## 4. Real defects found and fixed

Neither defect below was anticipated by the governing prompt. ### 4.1 `FourDaySessionDistanceAllocationPolicy.Allocate` / `V1FourDaySessionVolumeAllocationPolicy.Allocate` — hardcoded "at least one KEY_SESSION AND at least one EASY_SUPPORT" guard

This is the **sixth** real instance of this engagement's recurring "assumed every week has ≥1 of structural role X" defect family (`GEN.12` found 3, `GEN.17` found 1 more, `GEN.19` found 2 more in Runway/LongHorizon, none of them reachable). `V1FourDaySessionVolumeAllocationPolicy.Allocate` (line ~80) required `keySessionCount >= 1 AND easySessionCount >= 1` unconditionally before this phase; 2D's real Model B week (`GEN.11 §1`) always has **exactly one** non-`LONG_RUN` session — either a `KEY_SESSION` alone (Pattern A, `keySessionCount=1, easySessionCount=0`) or an `EASY_SUPPORT` alone (Pattern B, `keySessionCount=0, easySessionCount=1`) — never both. Every real 2D Core request at every representable week count therefore threw `CatalogSessionPrescriptionInfeasibleException("...does not match the V1 multi-key session shape.")` on **every** week, surfacing publicly as an opaque `INTERNAL_ERROR`.

**Fix**: generalized the guard from `keySessionCount<1 || easySessionCount<1` to `(keySessionCount+easySessionCount)<1` (at least one non-`LONG_RUN` session must exist, either role). The same generalization was applied one layer down in `FourDaySessionDistanceAllocationPolicy.Allocate`: the two independent `<1` throws were replaced with a single `both==0` throw, and the volume-split arithmetic was branched to route the entire non-long residual to whichever single role is present (previously the arithmetic unconditionally split residual volume between both roles via `Math.Max(...)`/rebalancing logic that assumed both were competing for share). `SplitEvenly` was taught to return an empty list for `count==0` (previously a division-by-zero risk, never reached before). The delta-absorption step (which folds any final 0.5km rounding remainder into `easyShares[^1]`) was branched to fold into `keyTotal` instead when no `EASY_SUPPORT` session exists that week. Every existing 3D+ caller always supplies both counts ≥1 simultaneously, so every branch above is a byte-identical no-op for them — confirmed by the full regression (§7), not merely asserted.

A third, narrower sub-defect in the same call chain: `V1FourDaySessionVolumeAllocationPolicy.Allocate`'s own trace-construction step unconditionally indexed `distances.KeySessionDistanceKm`/`FirstEasySupportDistanceKm`/`SecondEasySupportDistanceKm` (fixed `[0]`/`[0]`/`[1]` accessors) to build a diagnostic-only `SessionVolumeAllocationTrace` — which would throw `IndexOutOfRangeException` for 2D's now-legitimately-empty `KeySessionDistancesKm`/`EasySupportDistancesKm` list. Fixed by substituting `0.0` ("no such session this week") when the corresponding list is empty; confirmed safe because this trace record is diagnostic/display provenance only — the real per-session distance used for prescription is read via `allocation.KeySessionDistancesKm[ordinal]`/`EasySupportDistancesKm[ordinal]` directly in `CatalogSessionPrescriptionPlanner.DistanceFor`, never through this trace.

### 4.2 `CatalogFinalPrescribedPlanValidator.Validate` — hardcoded long-run-share cap proxy, wrong for 2D

A second, independent hardcode in the final defensive-validation stage: `var hardCap = boundPlan.Weeks...Sessions.Count == 3 ? 0.42d : 0.40d;` — a structural session-count *proxy* for "is this 3D" (0.42, the real `VolumeSafetyPolicy.ThreeDayIntermediate.LongRunHardCapShare`) versus a blanket `0.40` fallback for every other frequency, never consulting the real, candidate-specific `VolumeSafetyPolicy.LongRunHardCapShare` the upstream `CatalogVolumeAndLongRunPlanner` already enforces. This proxy was never wrong for 3D/4D/5D/6D (5D/6D's real cap, `0.36`, is always tighter than the `0.40` fallback, so the fallback never actually bound in practice) — but it was wrong for 2D: a 2D week's real session count is `2` (never `3`), so it fell into the `0.40` fallback branch, which is **tighter** than 2D's real, `GEN.11`-approved `0.60` cap (`VolumeSafetyPolicy.Beginner2D`/`Intermediate2D.LongRunHardCapShare`) — wrongly rejecting every valid 2D plan at every week count with `FINAL_WEEK_N_LONG_RUN_SHARE_EXCEEDS_CAP` for every week simultaneously.

**Fix**: replaced the session-count proxy with `ResolveLongRunHardCapShare(candidate)`, a new private helper mirroring `CatalogVolumeAndLongRunPlanner`'s own per-candidate `VolumeSafetyPolicy` dispatch exactly (`Beginner2D`/`Intermediate2D` for 2D, `ThreeDayIntermediate` for 3D, `FiveDayIntermediate`/`SixDayIntermediate` for 5D/6D, `ForAdvancedDaysPerWeek` for Advanced, `Default`/`BeginnerFourDay` otherwise) — every branch reproduces an already-existing, already-approved policy value verbatim; no new numeric authority. `Validate`'s signature was widened with a new `PlanCatalogCandidateSummary candidate` parameter (its sole caller, `CatalogFinalPrescribedPlanFinalizer.Complete`, already had `request.Candidate` in scope). Resolved values are byte-identical to the prior proxy's own values for every pre-`GEN.20` frequency — confirmed by full regression, not merely asserted; this tightens (from `0.40` to the real `0.36`) rather than loosens the check for 5D/6D, which cannot newly fail anything since the upstream planner already guarantees the real, tighter cap is never exceeded by construction.
