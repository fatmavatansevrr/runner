## 8. `phaseKey` versus `stageKey` terminology

No inconsistent or objectively-misleading usage was found in the Phase 4F.2 source, test, or documentation files. The type system consistently uses `StageKey` (matching Phase 4F.1's own already-established `GeneratedCatalogWeekPayload.StageKey` field), while every relevant type's XML doc comment explicitly disambiguates: for week-allocation purposes, "stage" = the catalog's `phaseKey` granularity (`FOUNDATION`/`BUILD`/`RACE_SPECIFIC`/`TAPER`), distinct from the catalog's finer, nested `stageKey` granularity (workout-selection progression steps like `GOAL_PACE_REHEARSAL`, which have no week-count allocation of their own and are out of scope for this phase). **No renames were performed** — none was necessary to prevent a real semantic defect, and the task explicitly forbids broad renames in this checkpoint.

**Deferred terminology cleanup (recorded, not undertaken)**: a future phase could consider renaming `StageKey` to `PhaseKey` throughout the Phase 4F.1 and 4F.2 contract types for closer alignment with the catalog's own vocabulary. This would be a cross-phase, breaking rename with no current runtime necessity, and is explicitly out of scope here.
